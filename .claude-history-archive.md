## 2. Size-band comp matching (sale transactions + LTR rents)

### Problem
When a user inputs a unit size (sqft), the estimator was matching comps only by bedroom-bucket, ignoring size — meaning a 450 sqft studio and a 900 sqft studio got averaged together. User's explicit direction: match comps to size (±10-15% band), OK to widen the lookback window to find enough of them, minimum 5 comps.

### Design
- `SIZE_BAND_PCT = 0.12` (±12%) used in both `app/api/sale-transactions/route.ts` and `app/api/ltr-rents/route.ts`.
- `withinSizeBand()` helper checks each transaction/contract's size field against `sizeSqft * (1 ± 0.12)`.
- **Two-pass fetch strategy** in both routes:
  - Pass 1: bedroom bucket AND size band. Windows escalate: `sizeSqft > 0 ? [180, 365, 730, 1095] : [180, 365, 730]` for sales, `[90, 365, 730, 1095] : [90, 365, 730]` for LTR. Needs `MIN_TXNS`/`MIN_CONTRACTS = 5`. If found, `sizeFilterApplied = true`.
  - Pass 2: fallback to bedroom-bucket ONLY (no size filter) if Pass 1 never reached 5, using the same escalating windows. Guarantees the estimator never comes back empty just because size data is thin.
- Cache key changed from `cacheKey(project, bedrooms)` to `cacheKey(project, bedrooms, sizeSqft)` in both routes — critical, because otherwise a size-filtered result could be served for a non-size-filtered request or vice versa.
- API responses now include a `sizeFilterApplied: boolean` so the UI/caller can show "matched by size" vs "bedroom-only" transparently.
- Known minor gap (accepted, not fixed): in `ltr-rents/route.ts`, `sizeFilterApplied` is only set on the `dda-live` success path inside the try block — the static-JSON fallback path doesn't set it. Cosmetic only.

### Wiring into UI
- `app/agent-tools/page.tsx`: computes `sizeSqftParam = Number(unitAreaSqft) > 0 ? `&sizeSqft=${encodeURIComponent(unitAreaSqft)}` : ""` and appends it to both the `/api/sale-transactions` and `/api/ltr-rents` fetch calls.
- `app/estimator/page.tsx`: in the `navigate()` function (report generation), added:
  ```ts
  if (form.sizeSqm) {
    const sizeSqft = form.sizeUnit === "sqft"
      ? Number(form.sizeSqm)
      : Math.round(Number(form.sizeSqm) * 10.7639);
    if (sizeSqft > 0) qs.set("sizeSqft", String(sizeSqft));
  }
  ```
  **Gotcha**: `form.sizeSqm` state actually holds the raw numeric input in whichever unit is currently toggled (`form.sizeUnit: "sqm" | "sqft"`), despite the misleading name. Confirmed via the input's onChange/toggle logic (resets `sizeSqm` to `""` on unit toggle).
  **Scope note**: `/estimator` only calls `/api/ltr-rents` — it never calls `/api/sale-transactions`. The size-band fix there only affects the LTR comp fetch, not sale comps (estimator doesn't display sale comps at all).

## 3. Two distinct, non-overlapping LTR code paths — do not conflate these

This was a major source of confusion mid-session and is the single most important architectural fact for a fresh session to know:

1. **`app/api/ltr-rents/route.ts`** — standalone "LTR Rental Benchmark" report card shown on `/estimator` and `/agent-tools`. Queries live DDA (Ejari) + falls back to static JSON (`lib/building-rents.ts`'s `lookupDLDBuilding`/`lookupDLDArea`). **Does NOT consult `BUILDING_LTR_OVERRIDES`.**
2. **`lib/estimator.ts` → `getLTRMarketRent()`** — used internally by `runEstimator()` to derive the STR estimator's `longTermRent` baseline (what's shown as "Estimated · [source]" in `app/report/page.tsx:1275`). Fallback chain:
   1. Exact DLD building match (live)
   2. Fuzzy DLD building lookup
   3. Area-level DLD actual rents (mapped community name, then raw DLD area name)
   4. **`BUILDING_LTR_OVERRIDES`** curated table (per-building manual overrides) ← this is where new manual data gets added
   5. Community-average benchmark table, or literal string `"Dubai market average"` as final fallback

When the user complains about "Estimated · Dubai market average" showing for a specific building, the fix is ALWAYS in path #2 (`lib/estimator.ts`), never in `api/ltr-rents/route.ts`.

## 4. DLD/DDA API client (`lib/dda-client.ts`)

Two datasets consumed via `ddaQuery()`:
- `dld_transactions-open-api` — sale transactions. Columns include both `project_name_en` AND `building_name_en`.
- `dld_rent_contracts-open-api` (Ejari) — rent contracts. Columns: `project_name_en`, `master_project_en`, `area_name_en`, plus landmark/metro/mall proximity fields. **No building-level field exists in this dataset at all.**

### Name resolution helpers
- `resolveDLDName()` — looks up a static mapping in `lib/data/dld-name-map.json`, normalized key (strips common suffix words).
- `buildDLDVariants()` — generates LIKE-prefix name guesses: BLVD/BOULEVARD swap, "AT <NAME>" prefix, strip "BY <DEVELOPER>", strip trailing token.

### Bug found and fixed: `fetchSaleTransactions()` ignored `building_name_en`
Root cause of "no live DLD sales data" for towers like Al Bateen Residences and G-24: the function fetched `building_name_en` in its column list but only ever filtered/searched on `project_name_en`. Some DLD records (especially individual towers within a larger complex) store the searchable name under `building_name_en`, not `project_name_en`.

**Fix**: refactored the internal `fetchForName()` helper to take a `field: "project_name_en" | "building_name_en"` param. New 3-tier search order:
1. `resolveDLDName()` canonical match on `project_name_en` (exact)
2. `buildDLDVariants()` guesses on `project_name_en` (prefix LIKE)
3. **NEW**: same variants on `building_name_en` (prefix LIKE) — fallback pass

This is deployed and confirmed working in production for both Al Bateen Residences and G-24 (both now return `"source":"dda-live"` with real transaction data).

`fetchProjectContracts()` (the Ejari/LTR fetcher) was deliberately NOT modified — there is no equivalent field to fall back to (see next section).

## 5. Structural limitation: DLD's Ejari dataset has no building-level field (confirmed, not fixable)

User's stated goal was "live LTR for every building in Dubai, not to miss a single one." Investigated via a temporary self-cleaning debug route (`app/api/debug-ejari-columns-temp/route.ts`, created then fully deleted) that directly introspected raw columns returned by `dld_rent_contracts-open-api`.

**Finding**: the dataset's only location-ish fields are `project_name_en`, `master_project_en`, `area_name_en` (plus landmark/metro/mall proximity) — no `building_name_en` or equivalent. Additionally, `project_name_en`/`project_number` are frequently `null` in the raw data.

**Conclusion communicated to user**: true "live LTR for every single building" is NOT achievable from DLD's public data — this is a DLD data-source ceiling, not a bug in this codebase. The realistic ceiling is: project-name match (when populated) → area-level average → curated per-building override table (see next section). Confirmed to user this isn't a naming/title issue (asked "would a title help?") — it's structural.

### Next.js routing gotcha hit during this investigation
A folder named `app/api/_debug-ejari-columns/` (leading underscore) 404'd — Next.js App Router treats underscore-prefixed folders as private and excludes them from routing. Fixed by renaming to `app/api/debug-ejari-columns-temp/` (no underscore). Route worked, was used once, then fully deleted (`rm -rf`) — confirmed 404 again post-deploy, i.e. cleanly removed from production.

## 10. Process notes / working conventions established this session

- Deploy exclusively via `npx vercel deploy --prod` from project root — never rely on git push triggering deploy (auto-deploy is disabled by design, per an earlier commit).
- For non-visual/server-side logic changes (like `getLTRMarketRent()`), verify with a standalone `npx tsx -e "..."` script that imports and calls the function directly, rather than attempting browser-based `preview_*` verification, which is reserved for actually-renderable UI changes.
- When sourcing fallback/override numbers, use WebSearch/WebFetch against real listing sites (Bayut, Property Finder) and cite the source in a code comment; omit specific bedroom sizes rather than guess-filling when sample data is thin, contradictory, or looks like an outlier.
- React controlled inputs make `preview_fill`/`preview_eval`-driven native-setter simulation unreliable for autocomplete/search-driven dropdowns bound to component state (value reverts because React's controlled binding wins over the simulated DOM event) — for this codebase's building-search dropdowns, prefer verifying the underlying data array directly (e.g. a Node script regex-extracting keys from `buildings-data.ts`) over attempting further browser automation on that specific input pattern.
- Next.js App Router: never use a leading underscore in an `app/api/` route folder name if you actually want it routable — it's treated as private/excluded by the framework.
